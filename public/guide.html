01
Core block

Make the working app your own

Goal: deploy an independent copy and improve the rule or wording that turns a signal into a useful review request.

Supplied

A deployable app, 24 synthetic orders, metric definitions and attention rules for negative margin, late delivery and high refunds. No earlier class project is required.

You change

One meaningful alert rule or message template. Keep the computed condition, the visible explanation and the outgoing request consistent.

  1. Copy the source to your own GitHub account or use Deploy your own copy. Open the resulting Vercel app and confirm that its dashboard loads.
  2. Inspect NS-1041: revenue is $1,200 and allocated cost is $1,320, giving profit of −$120. Distinguish observed facts from possible causes.
  3. Choose one change: adjust a documented alert threshold, improve the action title, or make the review question more specific. Update the actual logic or template, not just a decorative label.
  4. Redeploy and compare a matching and a non-matching record, or compare the original and revised message. Explain why your change improves a decision.

Ready when

  • Your own deployed URL loads the working template.
  • You can show one deliberate change and evidence that it behaves as intended.
  • The request preserves the source ID, relevant facts and a concrete question.
  • You distinguish a reason to investigate from proof of the cause.

02
Core block

Review, confirm and send a real event

Goal: send one intentional synthetic event to a personal ntfy topic and understand what the response does—and does not—prove.

Supplied

Server routes prepare a random topic locally, validate the request and send a real notification to ntfy. The review dialog and local outbox show the action and its current state.

You exercise and refine

Prepare your topic, review a request, cancel a rehearsal and confirm one real send. Improve the wording or feedback while keeping the mode and destination explicit.

  1. In your deployed app, choose Connect my test inbox and select live mode. The app prepares a random topic associated with this browser’s local configuration. No service login, API token or external topic-creation call is required.
  2. Choose a synthetic order and open its review dialog. Check the order ID, title, reason and personal topic destination. Cancel once and confirm that no event was sent.
  3. Reopen the review, edit the title or reason and confirm a single live action. Inspect the resulting local outbox entry.
  4. Separate accepted from verified received: a successful send response is not the independent read-back check. Choose Verify receipt in the next block before claiming that the message was independently confirmed.

Use synthetic data only. The topic URL and ID grant access to an unprotected test topic. Do not share them publicly or send credentials, student information or real customer data. Messages are cached by ntfy for about 12 hours; the topic itself does not expire on that schedule. Your local history can remain after the external message cache has expired.

Ready when

  • You can identify your own topic and the selected live or simulation mode.
  • Cancellation produces no external send.
  • A confirmed live action has a stable request ID and an honest outbox state.
  • You can explain that this is a real received message, not a ticket, email or database-backed shared history.
AI prompt · adapt to your project

Trace the supplied live review flow in this app. Explain how topic setup, confirmation, sending and local outbox storage work. Improve one piece of review or result wording so a user understands the destination and the difference between accepted and verified received. Keep simulation clearly labelled and ensure cancellation sends nothing. Do not add sign-in, paid services or credentials to the core exercise.

03
Core block

Inspect the HTTP path and verify the message

Goal: follow the event from your button to the destination, then change one payload field and verify the new result.

Supplied

Topic preparation, send and verify server routes. The server checks the synthetic order against the supplied dataset and reads the stored notification from ntfy using its anonymous polling API.

You inspect and adapt

Explain the request, response and received message. Add or refine one useful non-sensitive payload field in the validated server path and prove that it reaches the destination.

  1. Use Verify receipt for your sent event. Open your test inbox and locate the provider message ID and the embedded requestId and orderId. Verification reads the stored message; it does not send another one.
  2. Inspect the browser’s network activity or the server code. Identify /api/send-event and /api/verify-event, their input and response, and the external destination. The sent JSON is stored in ntfy’s message field; the provider also returns its own message id.
  3. Compare the received JSON with your reviewed title, reason and source order. Explain which values the user supplies and which are taken from the canonical synthetic dataset on the server.
  4. Add a useful field or clearer classification through the validated server path. Redeploy, create a fresh intentional request with a new request ID, verify it and compare the old and new messages.

Do not turn the template into an arbitrary relay. Keep the external host fixed to ntfy, validate topic and request IDs, enforce input limits, and keep the source limited to the synthetic dataset. The template is a bounded classroom exercise, not a general public messaging API.

Ready when

  • The app reports verified receipt only after reading the matching external message.
  • You can show the matching request ID, order ID and reviewed content.
  • Your changed field is present in a fresh message after redeployment.
  • You explain the difference between a send response, a verified message and completion of a business task.

You test and improve

Test the review and feedback, record observed results, and improve one failure or recovery message. Explain what must be added for durable multi-user duplicate protection.

05
Optional extension

Turn the event into a richer workflow

Goal: choose one extension: create a real business object, notify an approved destination, propose a file change, or add shared authorized persistence.

Supplied

A working HTTP pattern, source context, explicit review and read-back verification. These are the parts you can reuse.

You build

One new authorized integration or persistence layer, with separate status and real evidence. Service accounts or credentials may now be required.

GitHub issue or pull request

Create an issue in your own practice repository with a restricted server-side token. For a PR, propose a real file change, create a branch and inspect the diff. A transport helper does not supply your app’s authentication, authorization or durable request ledger.

Trello card

Create and verify a card in your own practice board. Prepare API authorization and keep the token server-side. Trello Free allows up to 10 collaborators per Workspace; avoid one shared class Workspace.

Teams Workflow or test email

Use a permitted test channel and current Teams Workflows, or a provider’s test recipients. Institutional permissions can block Teams. Resend test events demonstrate delivery scenarios, not a message read by a person.

Supabase persistence + authentication

Add sign-in, authorized server operations, access policies and a request table. Link requests to users and source records, preserve outcomes across devices, and implement durable duplicate handling.

  1. Choose one extension and define what it adds beyond capturing an HTTP event.
  2. Prepare its authorization and practice destination, or design the user access model for persistence. Keep all secret credentials out of browser code, chat, screenshots and commits.
  3. Implement and verify the real new result: issue/card URL, reviewed PR diff, approved test notification, or authorized database read after reload.
  4. Test one failure or access denial. Keep the original message’s result separate from the extension’s outcome.

Ready when

  • You can show a real result from the chosen extension and explain its permissions.
  • Your evidence does not confuse a received notification with a ticket or email.
  • Partial success is visible: a follow-up failure does not erase the original confirmed notification.

Practical limits of the free notification service

  • Use two live sends per student: one baseline event and one adapted payload. Verification reads existing messages. Use simulation for repeated failure tests.
  • ntfy’s published free limit is 250 messages per day, with visitor/IP request limits. Shared Wi-Fi or server hosting can share an allowance. The app’s two-event practice limit is not a durable global quota or an exactly-once guarantee.
  • Messages are cached for about 12 hours; the topic itself does not expire after 12 hours. After cache expiry, local history can remain even though the external message can no longer be read back.
  • A message is limited to 4,096 bytes before ntfy treats it as an attachment. Keep adapted event payloads small and preserve the server validation.
  • The topic is unprotected: its URL/name can grant read and write access. Use only the supplied synthetic records and keep the topic out of public screenshots.
  • Free external services can be unavailable. Continue UI/failure work in simulation, and mark live verification pending until a real message can be read back.

Optional HTTP diagnostic: Webhook.site can capture a raw request. Free URLs allow 100 captures and normally expire after seven days; creation is limited to one per minute per IP, so it is not the default shared-classroom route. It captures HTTP requests and does not create a ticket or email.
